# Track completion and download outputs

## Scope

Extend the existing one-shot Playwright CLI from confirmed submission through visible completion and local media persistence. Keep the dedicated visible Chrome profile, manual authentication/challenge handling, semantic locators, and public `https://suno.com/create` UI boundary. Do not inspect cookies, authorization headers, browser storage, request traffic, or private Suno APIs.

## Current structure

- `src/job.ts` validates one prompt and its generation options; the normalized object is the durable deduplication input.
- `src/submission.ts` fills the visible Create form, clicks once, and returns stable submission outcomes, but it does not preserve a receipt or observe later track cards.
- `src/cli.ts` launches the browser before any durable job lookup, reports `submitted`, then closes immediately.
- `src/runtime-paths.ts` contains all runtime paths under ignored `.suno-control/`; it currently exposes only the profile, shared download staging directory, and smoke artifacts.
- Existing controlled-browser fixtures in `test/submission.test.ts` already prove one-click submission, explicit challenge continuation, semantic locator behavior, and refusal to guess after an ambiguous post-click timeout.
- The attached Playwright revision documents that `launchPersistentContext` stores session data in its dedicated user-data directory, permits only one instance for that directory, and must not automate the normal Chrome profile (`docs/src/api/class-browsertype.md:329-352`).
- Installed Playwright 1.62.1 documentation specifies the supported download sequence: start `page.waitForEvent("download")` before clicking, then await the `Download` and call `download.saveAs(...)`; context closure otherwise removes temporary downloads (`docs/src/downloads.md:6-25`).

## Durable model

Add `src/tracking.ts` with a versioned, allowlisted `TrackedJob` schema. A deterministic SHA-256 identifier over the normalized `{ prompt, options }` JSON maps repeat invocations to `.suno-control/jobs/<id>/state.json`; media lives in that job's `outputs/` directory. The record contains only the identifier, original prompt/options, lifecycle history, submission attempt/confirmation timestamps, bounded observation/download attempt counters, visible track title or identifier, completion timestamp, actionable local error code/message, and relative output paths. It must never accept or serialize cookies, headers, storage state, arbitrary page HTML, or URLs containing query data.

Use lifecycle states `queued`, `running`, `completed`, `failed`, `blocked`, and `unknown`. Every transition appends one timestamped history entry and atomically rewrites state by writing a uniquely named same-directory temporary file with restrictive permissions, then renaming it over `state.json`. Loading treats JSON and every field as untrusted: manually validate the version, exact field types, status values, identifier equality, relative output paths, and path containment before use. Malformed or inconsistent state fails closed without submission.

Submission safety is independent of lifecycle status. Persist `submission.attemptedAt` immediately before the single Create click and `submission.confirmedAt` after visible acceptance. A restart may submit only a record with neither timestamp. A confirmed record resumes observation; a completed record returns its existing outputs without launching Chrome. An attempted-but-unconfirmed record becomes `unknown` with a review message and is never clicked again, closing the unavoidable crash window without risking duplicate generation.

## Visible observation

Extend `src/submission.ts` to return a small submission receipt identifying the newly added visible result container(s), without returning page content or network-derived data. Before implementation, recheck the authenticated visible Create page and centralize only confirmed role, accessible-name, test-id, and visible link/title locators. If unique result identity cannot be established, persist `unknown` rather than associating the wrong track.

Add `src/completion.ts` to scope all classification to the receipt's result containers. Classify visible `queued`/waiting markers, `running`/generating markers, explicit failure or account/rate restriction markers, and completion only when a track exposes its visible title/identifier plus an enabled Download control. Login or an interactive challenge maps to `blocked` with the existing manual action; contradictory, missing, ambiguous, or timed-out UI maps to `unknown`. Never persist raw page-provided error text; map confirmed markers to stable actionable messages.

Observation uses a fixed total deadline and maximum attempt count, with injected limits for tests. Each newly observed state is persisted immediately. No submission retry exists. Observation retries only re-read visible state; download retries are capped and stop immediately after an output path is recorded. Exhaustion records `unknown` and tells the user to inspect the visible browser and rerun tracking.

## Supported downloads

For each completed visible track, start `page.waitForEvent("download")` before clicking that track's exact Download control, await the event, check `download.failure()`, and save to a unique temporary file inside that job's `outputs/` directory. Derive a conservative filename from the visible title/identifier and `download.suggestedFilename()` using `path.basename`, an allowlisted character sanitizer, a bounded length, and a safe fallback; resolve and verify containment before every write.

Prevent overwrites with `copyFile(temp, candidate, COPYFILE_EXCL)`, adding a numeric suffix only on `EEXIST`, then remove the temporary file. Record the relative final path atomically only after persistence succeeds. On restart, an existing recorded path must resolve inside the job directory and exist before it is treated as downloaded; otherwise retry only the missing download within its bound. Multiple completed tracks receive separate metadata entries and collision-safe files.

## CLI integration

Update `src/runtime-paths.ts` with a contained `jobs` root. Update `src/cli.ts` to create/load state before browser launch, short-circuit completed jobs, pass a pre-click persistence callback into submission, persist the receipt and confirmed timestamp, run completion tracking, and print only stable status/action messages plus safe job/output-relative identifiers. Prompt/style contents and browser/session details remain absent from terminal output.

Map completed to exit `0`; retain existing pre-submission exit codes; use distinct nonzero exits for `failed`, `blocked`, and `unknown`. Always close the browser context. A rerun of queued/running/blocked/unknown confirmed work observes the existing receipt and never calls submission; if the visible identifier cannot reacquire exactly one result container, fail `unknown` rather than selecting the newest card.

## Risks

- Suno's result-card accessibility can change; centralized semantic locators and exact receipt matching convert drift into `unknown` instead of downloading another job's media.
- A crash after Create but before confirmation cannot prove acceptance; the pre-click attempt marker deliberately favors review over duplicate generation.
- The deterministic job identifier deduplicates identical normalized inputs; intentionally regenerating identical inputs is outside this phase and must not bypass saved-state safeguards.
- Local metadata contains prompts and downloaded media; restrictive file creation, ignored runtime paths, contained filenames, and no terminal echo limit accidental exposure, but other processes under the same OS account remain trusted.
- Download completion and state persistence are separate operations; temporary files and missing-path reconciliation make restart safe without overwriting existing media.
