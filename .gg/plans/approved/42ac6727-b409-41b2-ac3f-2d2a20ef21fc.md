# Assisted Suno Preparation Mode

## Goal

Add a separate `npm run assist -- ...` path that opens the dedicated persistent Chrome profile, reaches Suno Create, and visibly prepares every requested field at a fixed conservative cadence. The automation must stop after preparation, print a clear review message, and remain idle until the user closes the browser. Only the user may click Create.

This mode improves operator control; it is not an anti-detection or terms-compliance claim. It must not add stealth, randomization, proxying, CAPTCHA solving, automated submission, result observation, or downloading.

## Local baseline

- `src/main.ts:8-13` always enters the queue runner and `PlaywrightSunoAdapter`, whose session exposes submit, observe, and download capabilities.
- `src/suno/preparation.ts:68-109` already navigates and fills fields, but its dependency path uses `createFormLocators` from `src/suno/selectors.ts`.
- `src/suno/selectors.ts:40-50` places editable controls and the Create locator in one returned object, so it cannot satisfy a strict assisted-mode capability boundary.
- `src/suno/submission.ts:59-71` owns the single Create click and post-click result observation; assisted mode must never import or reach this module.
- `src/suno/playwright-adapter.ts:38-70` owns submission, completion observation, and downloads; assisted mode must bypass this adapter and the queue runner entirely.
- `src/cli/parse.ts:28-33` already provides validated single-job parsing suitable for assisted mode.
- `src/suno/browser.ts:11-22` already opens visible installed Chrome with the dedicated persistent profile.
- `test/smoke-boundary.test.ts:10-43` provides an existing dependency-graph guard pattern to reuse for stronger no-submit assertions.
- Installed Playwright 1.57.0 supports delayed sequential key presses, but assisted mode will not use keyboard press APIs because prompts may contain newlines and Enter must be structurally impossible.

## Design

### Separate executable path

Create `src/assist-cli.ts` and expose it as `npm run assist`. It will:

1. Parse exactly one job through `parseSunoJob`; queue manifests, concurrency, retries, repositories, and output stores remain unavailable.
2. Launch the existing persistent visible Chrome profile through `launchSunoBrowser`.
3. Call the assisted preparation capability.
4. Handle login or an interactive challenge only through visible manual completion and a terminal continuation prompt; terminal input is never forwarded to the page.
5. On readiness, print that automation has stopped and the user must review and click Create manually.
6. Await only browser-context closure, without reading page URL, DOM, network traffic, results, status, or downloads after readiness.

The process exits when the user closes the dedicated browser. Signals may close the context for cleanup, but there is no post-ready page callback.

### Structural no-submit boundary

Physically split non-account controls from submission controls:

- Add `src/suno/form-controls.ts` containing only Advanced, More Options, prompt/style fields, mode radios, and model controls.
- Add `src/suno/page-state.ts` containing login/challenge locators and create-page entry classification without Create, result, receipt, or download locators.
- Keep Create, submission-result, result-container, receipt, and download locators in `src/suno/selectors.ts`; existing submission/completion code continues to consume them.
- Refactor `src/suno/preparation.ts` to consume the shared non-submit controls and entry classifier while preserving existing submission behavior.
- Add `src/suno/assistance.ts` importing only the non-submit controls, page-state capability, job type, and timing helpers. It must not import `selectors.ts`, `preparation.ts`, `submission.ts`, `completion.ts`, `diagnostics.ts`, `playwright-adapter.ts`, queue code, repositories, or output stores.

The assisted orchestration receives a restricted field-control object for filling. No Create locator, result locator, generic submission adapter, keyboard object, or post-submit observer appears in its capability interface.

### Conservative visible cadence

Use fixed documented pacing for usability, not random “humanization”:

- Pause 1,000 ms between discrete control actions.
- Progressively fill text at 75 ms per character using repeated `Locator.fill(prefix)` calls.
- Never call `press`, `pressSequentially`, `keyboard`, or dispatch key events.
- Preserve multiline prompt text through `fill`; newline characters therefore cannot become Enter key events.
- Apply the existing field semantics: vocal prompt, optional style, optional exact model; instrumental mode combines prompt and optional style in the style field.
- Inject the sleeper/cadence into the preparation function so tests use zero real delay while proving the exact order and configured timing.

### Hard stop

A successful assisted preparation returns a terminal `ready-for-review` outcome. The CLI then drops all page/control references and waits only for the browser context’s `close` event. It does not create durable job state because no remote account action has occurred and it cannot know what the user does afterward.

Login, challenge, changed-UI, browser-launch, and invalid-input outcomes use concise distinct exit messages. A detected login/challenge may be manually resolved once before preparation resumes; no automatic retry loop is introduced.

## Tests

1. A fixture form records Create clicks, native form submissions, Enter key events, result reads, and download reads.
2. Vocal mode visibly fills prompt/style/model in order and records exact fixed sleeps.
3. Instrumental mode selects instrumental and fills the combined description correctly.
4. A multiline prompt containing newline characters produces zero Enter events and zero submissions.
5. Preparation returns with Create untouched and with no result, status, network, or download observation.
6. Login and challenge paths require terminal/manual continuation and never forward terminal Enter to Playwright.
7. Changed UI fails closed before any requested field is partially submitted.
8. Closing the browser ends the CLI; readiness itself does not close the browser.
9. The static dependency walk rooted at `src/assist-cli.ts` excludes submission, completion, diagnostics, queue execution, repositories, output stores, and the Playwright automation adapter.
10. The same dependency graph contains no Create locator/text, submit method, result/download locator, `keyboard`, `.press(`, or `pressSequentially` page action.
11. Existing submission and smoke tests continue proving their current independent behavior.

## Risks and controls

- **Terms and challenge risk:** Visible pacing does not authorize browser automation or prevent Cloudflare challenges. README wording must state this plainly.
- **Accidental Enter:** Progressive `fill` is used instead of all keyboard APIs, including for multiline values.
- **Boundary erosion:** A source dependency-graph test fails if assisted mode later imports account-action modules or forbidden locator/action vocabulary.
- **Duplicate functionality:** Only the small action policy remains assisted-specific; navigation classification and non-submit locator definitions are shared.
- **UI drift:** Exact semantic locators fail closed as `changed-ui`; no fallback selector may approach Create.
- **Unexpected manual action:** Once ready, user activity is deliberately outside automation state; the process observes only browser closure.
