# Lock the August 2026 baseline and module contracts

## Scope

Record a dated, source-backed Playwright and Suno UI baseline, then make the existing CLI's dependency direction enforceable. Preserve the visible, dedicated Chrome profile; manual authentication and challenge handling; bounded queue; durable no-duplicate submission behavior; redacted diagnostics; and contained, non-overwriting downloads. Do not submit a live generation, consume credits, inspect session storage/cookies/tokens/network traffic, automate challenges, or use private Suno APIs.

## Verified starting point

- The repository is clean on `main` at `d222d14`. It currently pins `playwright` 1.62.1, declares Node `>=20`, and runs CI on Node 20 for Windows and Ubuntu.
- Official Playwright release notes currently identify 1.62 as the newest feature release; GitHub marks 1.62.1 as Latest, released 30 July 2026: `https://playwright.dev/docs/release-notes` and `https://github.com/microsoft/playwright/releases/tag/v1.62.1`.
- Official system requirements for 1.62 list the latest Node 22.x, 24.x, or 26.x, so the implementation will choose Node 22 as the minimum supported runtime and align `package.json`, CI, and documentation: `https://playwright.dev/docs/intro` and `docs/src/intro-js.md:303-308` at tag `v1.62.1`.
- Playwright 1.62.1's official `browsers.json` pins Chromium revision 1234, browser version 151.0.7922.34: `https://raw.githubusercontent.com/microsoft/playwright/v1.62.1/packages/playwright-core/browsers.json`.
- The attached Playwright source at revision `d4e1023f6c03a8dced50eb3db88c2217e7c1a86a`, `docs/src/api/class-browsertype.md:329-352`, confirms persistent contexts store cookies/local storage in the user-data directory, permit one browser instance per directory, and must use a dedicated profile rather than normal Chrome data.
- Current boundaries are only partial: `job.ts` mixes domain validation with argv/manifest I/O; `tracking.ts` mixes pure transitions with disk persistence and downloads; `cli.ts` imports Playwright and concrete browser functions; selectors are repeated across `browser.ts`, `preparation.ts`, `submission.ts`, and `completion.ts`.
- Existing `test/smoke-boundary.test.ts` already walks imports to prove the live smoke path cannot reach submission. This standard-library graph approach can enforce all new boundaries without another dependency.

## Baseline record

Add `docs/baseline-2026-08.md` as the durable implementation baseline. Record the verification date, Playwright stable version and release URL, supported Node lines and chosen project runtime, Chromium revision/version, persistent-profile source, local package-lock evidence, and the exact installed commands used for confirmation.

The same document will contain a sanitized Suno inspection table for creation, authentication, naturally occurring challenge, generation status, and download controls. Each row records the visible route class, centralized selector key, observed state (`visible`, `absent`, or `not reachable without changing account state`), inspection date, and confidence. It must explicitly record `submitted=false` and `creditsConsumed=false`; absence is evidence, not permission to invent a selector.

Use the existing visible dedicated profile and a non-submitting inspection entry point. Navigation, visibility/count probes, screenshots, and opening non-destructive tabs are allowed. Filling or clicking the Create control, triggering a challenge, generating a track, modifying an existing track, or downloading media during baseline inspection is forbidden. Existing result cards may be inspected read-only. Local screenshots remain ignored under `.suno-control/` because they can expose account details; only fixed selector keys, bounded counts, and location classes enter the checked-in record.

If authentication is unavailable, first record the anonymous/login state. Authenticated creation/status/download inspection cannot be claimed until a person signs into the dedicated visible profile; that is the only expected human-action blocker. A challenge is recorded only if it appears naturally and remains manual.

## Target module layout

Use directories only where they establish a tested dependency zone; avoid a framework or dependency-injection container.

- `src/domain/job.ts`: `SunoJob`, generation options, deterministic normalization/identifier, tracked job/output/receipt types, lifecycle transitions, resume decisions, and pure saved-state validation. It imports no Playwright, filesystem, CLI parsing, paths, or adapters.
- `src/application/contracts.ts`: narrow `JobRepository`, `OutputStore`, `SunoAutomation`, and `SunoSession` contracts plus semantic outcomes. Contracts use domain values and opaque session/job handles, never Playwright `Page`, `Locator`, `BrowserContext`, or `Download`.
- `src/application/run-jobs.ts`: current queue/session workflow and outcome mapping. It depends only on domain values, contracts, and generic queue logic; persistence checkpoints remain explicit before a possible Create click.
- `src/cli/parse.ts` and `src/cli/presentation.ts`: bounded argv/manifest parsing and stable redacted terminal messages/exits. They depend on domain/application contracts, not Playwright or Suno selectors.
- `src/config.ts`: supported runtime constants, Suno public origin/create URL, time/attempt limits, and contained runtime/job path resolution. It contains no browser actions.
- `src/persistence/local-job-repository.ts`: validated load, restrictive atomic save, state-path containment, and output-existence reconciliation implementing `JobRepository`. It may import domain/config, never Playwright or Suno code.
- `src/downloads/local-output-store.ts`: filename sanitization, contained temporary/final paths, exclusive collision handling, and file existence implementing `OutputStore`. It receives bytes or a temporary file contract, never a Playwright locator/page.
- `src/suno/selectors.ts`: the sole source of all Suno role/name/test-id/CSS locators and URL-state classifiers for creation, login, challenge, submission status, result identity, generation status, and download controls.
- `src/suno/playwright-adapter.ts`: persistent Chrome launch, preparation, single guarded submission, visible completion observation, Playwright download acquisition, redacted probes, and semantic mapping to `SunoAutomation`. Only this zone imports Playwright and selectors.
- `src/main.ts`: the composition root that creates concrete configuration, repository, output store, and Playwright adapter, then invokes the CLI/application workflow. `package.json` starts this file; tests call injected CLI/application functions directly.

Existing files may be moved or reduced as part of this consolidation rather than retained as forwarding wrappers. Keep `src/queue.ts` as browser-agnostic scheduling logic. Preserve public exports only where current tests or package entry points require them, and update those callers in the same change.

## Contracts and dependency direction

`JobRepository` exposes load/save/output-existence operations keyed by validated domain identifiers. `OutputStore` exposes existence and collision-safe persistence under a job's output root. `SunoAutomation.open()` yields a semantic session that can execute `submit` or `observe` and close; execution receives a mandatory pre-submit checkpoint callback so durable `attemptedAt` is still saved immediately before the adapter clicks Create. Semantic results carry only fixed status codes, bounded receipt identity, tracked outputs, and redacted diagnostic facts.

The dependency direction is `main -> cli/application -> domain/contracts`, with `main -> local adapters -> contracts/domain/config`. Domain imports nothing inward. Persistence and downloads never import Playwright or Suno. CLI parsing/presentation never imports Playwright, selectors, or concrete adapters. The Playwright adapter may depend on contracts, domain, config, output storage, and centralized selectors.

A future official API adapter implements `SunoAutomation` and reuses `run-jobs.ts`, lifecycle transitions, repository, output store, and CLI presentation unchanged. API-specific authentication, polling, and response mapping stay in that adapter; no speculative API implementation is added now.

## Refactoring approach

Move pure types and transitions first, preserving existing behavior through focused tests. Then extract local state and output operations behind contracts. Consolidate locator construction before moving browser behavior, so every UI operation has one selector owner. Finally move orchestration out of `cli.ts` and leave `main.ts` as the only concrete wiring point.

Keep the no-duplicate invariant: state is created before browser launch, `attemptedAt` is atomically persisted before Create, ambiguous submission becomes review/unknown, and confirmed jobs only observe. Adapter errors map to existing stable exits without leaking page text, URLs, account data, prompts, or raw exceptions.

## Enforceable architecture checks

Add `test/architecture.test.mjs` using only `node:fs`, `node:path`, and assertions. Parse relative static imports, build the complete `src` graph, and fail with a readable path for any cycle. Apply zone allowlists to reject:

- any Playwright import outside `src/suno/`;
- any Playwright/Suno/CLI import from domain, persistence, or downloads;
- any concrete adapter or selector import from CLI/application code;
- any Suno locator constructor (`getByRole`, `getByTestId`, or raw `locator`) outside `src/suno/selectors.ts`, except generic adapter operations on locators returned by that module;
- any submission-capable dependency reachable from the baseline/smoke inspection entry point.

Retain the existing prohibited-technique checks for cookies/storage state, request interception, private APIs, stealth, forced input, and automated challenge behavior. Add the architecture test to `npm test`, so CI on both operating systems enforces it.

## Risks

- Suno state selectors may not all be visible in one account/session. Record unobserved states honestly and fail closed at runtime rather than broadening selectors from guesses.
- Refactoring the pre-click checkpoint could reintroduce duplicate submissions. Keep it in the semantic adapter contract and cover crash/ambiguous paths before moving browser code.
- Centralizing all selectors can create an oversized file; keep small named factories grouped by UI state, without adding a selector abstraction layer.
- A local inspection screenshot may contain account data. Keep it ignored, never parse arbitrary page text into the baseline, and check the staged diff before completion.
- Node 20 is accepted by package metadata but no longer listed in current official system requirements. Aligning to Node 22 is an intentional support change and must be reflected in CI and README.
